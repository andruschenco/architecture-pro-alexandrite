# Задание 5. Архитектурное решение по кешированию 

## 1. Мотивация

### Проблемы

- Операторы жалуются на низкую скорость загрузки дашборда MES (страница со списком заказов в работе). Даже после добавления фильтра по статусам и пагинации время отклика остаётся высоким.
- Заказы обрабатываются медленно, что вызывает недовольство клиентов и партнёров.
- Нагрузка на базу данных MES растёт: каждый оператор постоянно обновляет страницу, а также изменяются статусы заказов (приходят новые расчёты, операторы берут заказы, завершают этапы).

### Цели кеширования

- Сократить время отклика дашборда с десятков секунд до < 1 секунды.
- Снизить нагрузку на базу данных MES (сейчас один инстанс БД работает и на запись, и на чтение).
- Улучшить пользовательский опыт операторов и ускорить обработку заказов.

### Какие данные кешировать

- **Список заказов для дашборда** (отфильтрованный по статусам, отсортированный по дате). Это наиболее часто читаемая информация.
- **Количество заказов по статусам** (счётчики для фильтров) – можно кешировать отдельно.
- **Детали заказа** (при открытии карточки) – хотя это менее критично, но тоже можно кешировать.

### Что кешировать не нужно

- **Расчёт стоимости** – зависит от 3D-модели и меняется при каждом заказе, кеширование неэффективно.
- **Промежуточные статусы** – они меняются часто, но можно кешировать финальные результаты (например, завершённые заказы).

## 2. Предлагаемое решение

### 2.1. Тип кеширования: серверное (внутреннее)

Выбираем **серверное кеширование**, потому что:
- Клиентское кеширование (на стороне браузера) не решит проблему нагрузки на БД и не ускорит первый запрос.
- Данные общие для всех операторов, кеш должен быть единым.
- Серверное кеширование позволит управлять инвалидацией централизованно.

### 2.2. Паттерн кеширования: **Cache-Aside (Lazy Loading)**

**Описание паттерна:** при запросе данных приложение сначала проверяет кеш; если данных нет (cache miss), загружает их из БД, сохраняет в кеш и возвращает. При обновлении данных (запись) приложение удаляет (или обновляет) соответствующие записи в кеше.

**Почему Cache-Aside:**
- Прост в реализации.
- Не требует сложной синхронизации между БД и кешем (данные загружаются только по требованию).
- Подходит для сценариев, где чтение происходит чаще, чем запись (что верно для дашборда).
- Позволяет избежать загрязнения кеша редко используемыми данными.

**Почему не другие паттерны:**
- **Write-Through** – при каждой записи синхронно обновлять кеш, что замедлит операции изменения статусов (а они тоже важны).
- **Refresh-Ahead** – избыточен, требует предсказания, какие данные понадобятся.

### 2.4. Стратегия инвалидации кеша

**Предлагаемая стратегия: программная инвалидация по ключу + временная (TTL).**

- **При изменении статуса заказа** (любой записи) – удаляем все ключи, связанные со списками заказов (например, `orders:list:*`), а также ключ деталей этого заказа.
- **TTL (время жизни) – 60 секунд** для списков заказов. Даже если инвалидация по каким-то причинам не сработала, кеш обновится автоматически через минуту.
- **Для счётчиков по статусам** – TTL 30 секунд, инвалидация по тем же событиям.

**Почему не другие стратегии:**
- **Временная инвалидация (только TTL)** – приведёт к тому, что операторы будут видеть устаревшие данные до 60 секунд, что неприемлемо для производственных задач.
- **Инвалидация по ключу (без TTL)** – риск бесконечного роста кеша, если из-за бага не будет удаления. TTL служит «страховкой».
- **Автоматическая инвалидация через триггеры БД** – сложнее в реализации, привязывает к конкретной СУБД.

### 2.5. Сравнительный анализ стратегий инвалидации

| Стратегия                                  | Преимущества                                                                                                   | Недостатки                                                                              |
|--------------------------------------------|----------------------------------------------------------------------------------------------------------------|-----------------------------------------------------------------------------------------|
| **Программная по ключу + TTL** (выбрано)   | – Гарантирует актуальность после каждого изменения<br>– TTL подстраховывает от ошибок<br>– Простота реализации | – Требует вызова инвалидации из кода<br>– При сбое приложения кеш может устареть до TTL |
| Только TTL                                 | – Очень просто<br>– Нет лишних вызовов                                                                         | – Данные устаревают до минуты<br>– Операторы могут не видеть новые заказы               |
| Write-Through (обновление кеша при записи) | – Кеш всегда актуален                                                                                          | – Замедляет запись (оператор ждёт)<br>– Сложность синхронизации                         |
| Инвалидация через БД (триггеры)            | – Не зависит от кода приложения                                                                                | – Привязка к БД<br>– Трудно отлаживать<br>– Не подходит для распределённых кешей        |

## 3. Дополнительное задание: альтернативные решения (если сложно выбрать)

### Решение 1 (основное): Redis как внешний кеш

| Параметр     | Описание                                                                                                                                                                                                 |
|--------------|----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| **Описание** | Выделенный сервер Redis (или кластер) для хранения списков заказов и счётчиков. MES обращается к Redis через библиотеку (например, StackExchange.Redis). Инвалидация – по ключам при изменении статусов. |
| **Плюсы**    | – Высокая производительность<br>– Поддержка сложных структур (списки, хэши)<br>– TTL и автоматическое удаление<br>– Возможность масштабирования                                                          |
| **Минусы**   | – Дополнительный компонент в инфраструктуре<br>– Требуется управление сериализацией                                                                                                                      |

### Решение 2: Встроенный кеш в памяти (например, MemoryCache в C#)

| Параметр     | Описание                                                                                                                                                           |
|--------------|--------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| **Описание** | Использовать `IMemoryCache` внутри MES (если MES работает как один инстанс). Кеш живёт в памяти процесса.                                                          |
| **Плюсы**    | – Не требует внешних сервисов<br> – Очень быстро (без сетевых вызовов)                                                                                             |
| **Минусы**   | – Не работает при нескольких инстансах MES (кеш не синхронизируется)<br> – Потеря кеша при перезапуске подов<br> – Не подходит для горизонтального масштабирования |

**Заключение:** для компании «Александрит», которая планирует переход в Kubernetes и горизонтальное масштабирование MES, **выбираем Решение 1 (Redis)**. Оно обеспечит согласованность кеша между несколькими экземплярами сервиса и ляжет в основу дальнейшего роста нагрузки.

## 4. Итог

Внедрение кеширования с помощью Redis по паттерну Cache-Aside и стратегией программной инвалидации + TTL позволит:
- Снизить время отклика дашборда MES с десятков секунд до 50–100 мс.
- Уменьшить нагрузку на базу данных в 5–10 раз.
- Повысить удовлетворённость операторов и ускорить обработку заказов.

**План реализации:**
1. Развернуть Redis (Managed Service в облаке или в кластере).
2. Добавить в MES клиентскую библиотеку Redis.
3. Реализовать методы чтения через Cache-Aside.
4. Добавить вызовы инвалидации при каждом изменении статуса заказа.
5. Настроить мониторинг (метрики попаданий в кеш, времени выполнения).
