# Задание 4. Архитектурное решение по логированию 

## 1. Анализ системы и выбор систем для логирования

На основе C4-диаграммы и описанных проблем (потеря заказов, долгая обработка, падение дашборда MES, жалобы партнёров) логирование необходимо внедрить во всех сервисах, где проходят бизнес-процессы и потенциальные точки отказа:

- **Онлайн‑магазин** (Vue + Java Spring Boot) – логирование действий клиента: создание заказа, загрузка 3D-модели, отправка формы.
- **CRM** (Vue + Java Spring Boot) – логирование подтверждения заказа продавцом, отправки в производство, закрытия заказа.
- **MES** (React + C#) – логирование расчёта цены, взятия заказа оператором, изменения статусов (производство, упаковка, отгрузка).
- **RabbitMQ** – логирование отправки/получения сообщений, dead‑letter, задержки.
- **Базы данных** (PostgreSQL) – логирование медленных запросов, ошибок подключения.

> На схеме C4 эти системы будут выделены красным цветом как «требующие логирования».

## 2. Список необходимых логов (уровень INFO)

Для каждого бизнес-события логируем структурированные JSON-записи с полями:

| Система          | Событие                                           | Поля                                                                   |
|------------------|---------------------------------------------------|------------------------------------------------------------------------|
| Онлайн‑магазин   | Создание заказа (INITIATED)                       | timestamp, customer_id, order_id, session_id, source_ip                |
| Онлайн‑магазин   | Загрузка 3D‑модели (FILE_UPLOADED)                | timestamp, order_id, file_size, poly_count, file_format                |
| Онлайн‑магазин   | Нажатие «Сделать заказ» (SUBMITTED)               | timestamp, order_id, total_price                                       |
| CRM              | Подтверждение заказа (MANUFACTURING_APPROVED)     | timestamp, order_id, manager_id, approval_time                         |
| CRM              | Закрытие заказа (CLOSED)                          | timestamp, order_id, reason, shipping_tracking                         |
| MES              | Получение заказа на расчёт (из очереди)           | timestamp, order_id, queue_name, message_id                            |
| MES              | Расчёт цены (PRICE_CALCULATED)                    | timestamp, order_id, calculation_duration_ms, poly_count, result_price |
| MES              | Оператор взял заказ (MANUFACTURING_STARTED)       | timestamp, order_id, operator_id                                       |
| MES              | Производство завершено (MANUFACTURING_COMPLETED)  | timestamp, order_id, operator_id, duration_in_production               |
| MES              | Упаковка (PACKAGING) и отгрузка (SHIPPED)         | timestamp, order_id, operator_id, shipping_date                        |
| RabbitMQ (агент) | Сообщение опубликовано / получено / в dead‑letter | timestamp, queue_name, exchange, routing_key, message_size, error      |

## 3. Использование других уровней логирования

- **ERROR** – любые исключения в API, сбои подключения к БД, ошибки при отправке в RabbitMQ.  
  Пример: `ERROR | order_id=12345 | failed to save to DB: timeout`
- **WARN** – повторные попытки отправки, долгие запросы (> SLA), превышение лимита очереди.  
  Пример: `WARN | order_id=12345 | retry #3 for price calculation`
- **DEBUG / TRACE** – включаются в dev-окружении для отладки; в prod не используются.

## 4. Мотивация внедрения логирования

**Почему нужно логирование?**

- **Скорость инцидентов** – сейчас разбор ошибок занимает дни, т.к. вся информация только от клиентов. Логи позволят найти корень за минуты.
- **Прозрачность процессов** – можно точно узнать, на каком этапе завис заказ (расчёт цены, ожидание оператора, доставка).
- **Данные для оптимизации** – агрегированные логи помогут выявить узкие места (медленные запросы, частые ошибки).
- **Безопасность** – логи доступа к чувствительным данным помогут обнаружить аномалии.

**Метрики, на которые повлияет логирование:**

| Тип         | Метрика                                        | Как повлияет                                                       |
|-------------|------------------------------------------------|--------------------------------------------------------------------|
| Бизнес      | **MTTR (Mean Time To Recovery)**               | Сократит время восстановления после сбоя с дней до часов.          |
| Бизнес      | **Завершённость заказов**                      | Позволит выявить и устранить потери заказов на этапах интеграции.  |
| Техническая | **Количество ошибок 5xx в API**                | Мониторинг по логам ошибок даст точные цифры (а не только алерты). |
| Техническая | **Длительность обработки сообщений в очереди** | Логи сообщений помогут обнаружить задержки и dead‑letter.          |
| Техническая | **Частота повторных попыток**                  | Укажет на проблемы с интеграциями (CRM ↔ MES).                     |

## 5. Приоритеты внедрения логирования (и трейсинга)

Поскольку команда не может сделать всё сразу, приоритеты:

| Очерёдность | Система        | Причина                                                                       |
|-------------|----------------|-------------------------------------------------------------------------------|
| **1**       | MES            | Самое узкое место, больше всего жалоб операторов, потеря заказов.             |
| **2**       | CRM            | Ключевой компонент для подтверждения заказов и эскалации.                     |
| **3**       | RabbitMQ       | Интеграционная шина – без логов очереди невозможно отладить потерю сообщений. |
| **4**       | Онлайн‑магазин | Важен для первых этапов заказа, но там меньше тайн.                           |
| **5**       | Базы данных    | Медленные запросы уже могут быть выявлены через стандартные инструменты БД.   |

> Трейсинг (Jaeger + OpenTelemetry) будет внедряться параллельно с логированием, начиная с MES и CRM, чтобы получить полную наблюдаемость (см. Задание 3).

## 6. Предлагаемое решение

### 6.1. Технологический стек

- **Сбор логов** – **Fluentd** (или **Filebeat**) как агенты на каждом узле Kubernetes (DaemonSet). Они читают stdout контейнеров и пересылают в центральный сервер.
- **Хранение и поиск** – **ELK** (Elasticsearch, Logstash, Kibana) – зрелое решение, поддержка структурированных логов, мощный поиск, визуализация.
- **Альтернатива** – **Loki** + **Grafana** (более лёгкий, дешёвое хранение, хорошо с метками). Выбираем ELK для полноты функционала.
- **Доставка** – Logstash может обогащать логи, фильтровать и отправлять в Elasticsearch.

### 6.2. Компоненты и связи (схема)

**Новые компоненты (выделены зелёным на C4‑диаграмме):**
- **Fluentd** – агент на каждом узле.
- **Elasticsearch** – кластер хранения логов.
- **Kibana** – веб‑интерфейс для поиска и дашбордов.

**Связи:**
- Все бизнес‑контейнеры (shop, CRM, MES) → выводят логи в stdout → Fluentd собирает.
- Fluentd → Logstash (опционально) → Elasticsearch.
- Kibana → Elasticsearch (запросы).
- Администраторы / поддержка → Kibana (по HTTPS).


### 6.3. Безопасность

- **Чувствительные данные** – в логах не должны появляться пароли, персональные данные (ФИО, паспортные данные). Использовать `customer_id` вместо имени.
- **Доступ к Kibana** – только через корпоративный VPN, с аутентификацией (LDAP / OAuth2). Роли: `support` – просмотр логов, `admin` – настройка индексов и дашбордов.
- **Шифрование** – трафик между Fluentd и Elasticsearch через TLS, индексы Elasticsearch зашифрованы на диске.
- **Ротация и аудит** – доступ к логам логируется в отдельном индексе.

### 6.4. Политика хранения

- **Размер индексов** – создавать ежедневные индексы (например, `logs-2026-05-20`).
- **Время хранения** – 30 дней для логов уровня INFO, 90 дней для ERROR/WARN.
- **Ёмкость** – ориентировочно 10 ГБ в день (при 1000 заказах/день). Использовать роллинг индексов и удаление старых через ILM (Index Lifecycle Management).
- **Для аудита безопасности** – отдельный индекс с длительным хранением (1 год).

### 6.5. Система анализа и алертинг

- **Алерты на основе логов** – настроены в Kibana через Watcher (или через Elasticsearch Watcher, или через внешний Prometheus + Alertmanager).
- **Примеры аномалий и алертов:**
  - **Внезапный рост ошибок 5xx** – более 5% за 5 минут → отправлять в чат поддержки.
  - **Повторяющиеся Dead‑letter в RabbitMQ** – количество > 10 за минуту → критический алерт.
  - **Заказ завис в статусе > SLA** – событие с уровнем WARN (например, `MANUFACTURING_APPROVED` дольше 24 часов) → открывать тикет в Jira.
  - **Слишком частые попытки входа в админку** – более 10 неудачных логинов за минуту → сигнал о брутфорсе.
- **Аномалии через машинное обучение** (опционально): можно подключить платный модуль Elasticsearch (или использовать OpenSearch). Например, детекция внезапного роста количества заказов на 1000% – возможная DDoS‑атака.

## 7. Дополнительное задание: критерии выбора технологии

| Критерий                 | ELK (Elasticsearch, Logstash, Kibana)                | Loki + Grafana                                  | Splunk                         |
|--------------------------|------------------------------------------------------|-------------------------------------------------|--------------------------------|
| **Лицензия**             | Elastic License (частично открыта)                   | AGPLv3 (открытая)                               | Проприетарная, дорогая         |
| **Архитектура**          | Elasticsearch + Logstash + Kibana                    | Loki (индексирует только метки) + Grafana       | Собственная, тяжёлая           |
| **Сложность установки**  | Средняя (можно через оператора)                      | Низкая                                          | Высокая (требует лицензии)     |
| **Поиск по содержимому** | Полнотекстовый (быстрый)                             | Ограниченный (требуется дополнительный парсинг) | Очень быстрый, но дорогой      |
| **Хранение логов**       | На диске (можно использовать S3)                     | S3 / облачное                                   | Своё, очень дорогое            |
| **Алертинг**             | Watcher (платный) или внешний                        | Встроен в Grafana                               | Встроен (отличный)             |
| **Визуализация**         | Kibana (мощная)                                      | Grafana (удобная для метрик+логов)              | Splunk (очень дорогой)         |
| **Цена (владелец)**      | Бесплатно для небольших объёмов; Enterprise – платно | Полностью бесплатно                             | Очень дорого, не для стартапов |

**Вывод для «Александрит»:**  
Учитывая ограниченный бюджет и желание открытости, **ELK** – предпочтительнее: он даёт полнотекстовый поиск, гибкое хранение и широкое сообщество. **Loki** можно рассмотреть, если команда уже активно использует Grafana, но поиск по содержимому там слабее. **Splunk** не подходит из‑за лицензионных затрат.

## 8. Связь с мониторингом и трейсингом (полная наблюдаемость)

Логирование является частью общей стратегии **Observability**. В дополнение к логам мы внедряем:
- **Мониторинг метрик** (Prometheus + Grafana) по методологии **RED** (Requests Rate, Errors, Duration) для API и **USE** (Utilization, Saturation, Errors) для инфраструктуры – см. Задание 2.
- **Трейсинг** (Jaeger + OpenTelemetry) для отслеживания полного пути заказа через сервисы – см. Задание 3.

Вместе эти три компонента позволят команде «Александрит» быстро выявлять и устранять проблемы, повысить надёжность системы и снизить число жалоб клиентов.
