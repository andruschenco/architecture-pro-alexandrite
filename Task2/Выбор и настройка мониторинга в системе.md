# Задание 2. Мониторинг системы «Александрит»

## 1. Мотивация

**Почему нужен мониторинг?**

- **Рост нагрузки** – ежемесячно +100 заказов, нагрузка растёт линейно, а IT-инфраструктура не масштабируется.
- **Просроченные заказы** – клиенты жалуются, что заказы делаются месяцами вместо 3 недель, но причина не в производстве, а в IT.
- **Открытое API** – партнёры могут «заваливать» систему заказами, нет контроля.
- **Падение производительности** – дашборд MES тормозит, фильтр и пагинация не помогают.
- **Потеря контрактов** – за первый месяц после открытия API потеряны крупные партнёры.

**Что даст мониторинг:**

- **Раннее обнаружение проблем** – сможем заметить рост очередей, падение отклика, ошибки API до жалоб клиентов.
- **Обоснованное масштабирование** – данные о нагрузке помогут понять, когда и какие ресурсы увеличивать.
- **Анализ времени жизни заказа** – увидим, на каком этапе заказ задерживается (отсутствие временных меток сейчас).
- **Оптимизация дашборда MES** – метрики помогут выявить, почему страница тормозит (медленные запросы, большой объём данных).
- **Предотвращение перегрузок от партнёров** – rate limiting и мониторинг RPS по каждому партнёру.

## 2. Выбор подходов к мониторингу

| Часть системы                                | Выбранный подход                           | Обоснование                                                                                                                   |
|----------------------------------------------|--------------------------------------------|-------------------------------------------------------------------------------------------------------------------------------|
| **Онлайн-магазин (B2C)**                     | RED (Requests Rate, Errors, Duration)      | Пользовательский веб-сервис, важен пользовательский опыт – частота запросов, ошибки, задержки.                                |
| **CRM (внутренняя)**                         | RED + USE (для ресурсов)                   | RED для API, USE для серверов/БД – т.к. CRM – внутренний сервис для продавцов, но тоже критичен.                              |
| **MES (производство)**                       | RED + USE + специальные метрики по заказам | MES – потенциальное узкое место; RED для API, USE для серверов/БД, плюс метрики времени обработки заказа и состояния очереди. |
| **RabbitMQ**                                 | USE (утилизация, насыщенность, ошибки)     | Очередь – критический компонент интеграции, нужно отслеживать длину очереди, dead-letter, сообщения in flight.                |
| **Инфраструктура (CPU, память, диск, сеть)** | USE                                        | Классический подход для ресурсов.                                                                                             |

## 3. Выбранные метрики и обоснование

### 3.1. Метрики уровня приложений (API)

| Метрика                                           | Зачем                                                                                 | Ярлыки (labels)                                                   |

| **Response time (latency) для shop/CRM/MES API**  | Ключевой показатель пользовательского опыта, выявление медленных запросов             | `quantile` (p50, p95, p99), `endpoint`, `status_code`             |
| **Number of HTTP 200 / HTTP 500**                 | Отслеживание доли успешных/ошибочных запросов                                         | `endpoint`, `service`                                             |
| **Number of simultaneous sessions**               | Контроль загрузки сессионного хранилища, возможные утечки                             | `service`                                                         |

## 4. План действий (драфт технического задания)

1. **Настроить сбор метрик**
  - Развернуть Prometheus (или Managed Service в облаке) как хранилище метрик.
  - Внедрить клиентские библиотеки Prometheus в Java Spring Boot (онлайн-магазин, CRM) и в C# (MES).
  - Установить агенты Node Exporter для сбора системных метрик (CPU, память, диск).
  - Настроить экспортёр для RabbitMQ (rabbitmq-prometheus).
  - Настроить экспортёр для БД (PostgreSQL exporter) для сбора метрик БД.
  - Для RabbitMQ и БД использовать pull-модель Prometheus.

2. **Визуализация и алертинг**
  - Развернуть Grafana, подключить Prometheus как источник.
  - Создать дашборды:
    - Общий дашборд «Состояние системы» (RPS, ошибки, latency, ресурсы).
    - Дашборд «Заказы» (время жизни заказа по статусам, количество заказов в работе).
    - Дашборд «Очереди RabbitMQ» (dead-letter, in flight, длина очереди).
    - Дашборд «API партнёров» (RPS по каждому партнёру, ошибки).
  - Настроить алерты (Alertmanager) на:
    - Ошибки 5xx > 1% за 5 мин.
    - Latency p95 > 5 секунд.
    - Длина очереди RabbitMQ > 1000.
    - Использование CPU/памяти > 80% на 10 мин.
    - Заказ «завис» в статусе > SLA (например, >1 дня в `MANUFACTURING_APPROVED`).

3. **Логирование (для времени жизни заказа)**
  - Настроить централизованный сбор логов (ELK или Loki).
  - Добавить логирование переходов между статусами с меткой времени и ответственным пользователем.
  - Построить дашборд «Время жизни заказа» на основе логов.

4. **Тестирование и внедрение**
  - Развернуть стенд в dev-окружении, проверить сбор метрик.
  - Обучить команду работе с дашбордами (особенно операторов и продакт-менеджера).
  - Постепенно выкатывать в release и prod.

## 5. Показатели насыщенности и сценарии превышения

| Ресурс                 | Метрика насыщенности                                   | Пороговое значение       | Действие при превышении                                                                                                      |
|------------------------|--------------------------------------------------------|--------------------------|------------------------------------------------------------------------------------------------------------------------------|
| **CPU MES**            | Utilization (средняя за 5 мин)                         | > 80%                    | Увеличить число реплик MES (горизонтальное масштабирование), добавить алерт.                                                 |
| **Память MES**         | Utilization > 85%, рост swap/падания                   | > 85%                    | Увеличить память инстанса, проверить утечки, перезапустить под.                                                              |
| **БД (MES)**           | Количество активных соединений / max_connections > 80% | > 80%                    | Увеличить `max_connections`, оптимизировать пул соединений, добавить реплику для чтения.                                     |
| **Размер диска БД**    | Использование > 90%                                    | > 90%                    | Расширить том (cloud volume), удалить старые данные, настроить архивацию.                                                    |
| **Очередь RabbitMQ**   | Длина очереди (ready + unacked)                        | > 1000                   | Задействовать горизонтальное масштабирование MES, увеличить consumer'ов, проверить dead-letter.                              |
| **API партнёра (RPS)** | RPS для конкретного partner_id                         | > 50 RPS (настраивается) | Включить rate limiting на уровне API Gateway, отправить уведомление партнёру, временно заблокировать при превышении 100 RPS. |

**Что должно произойти при превышении (автоматизация):**
- Создать тикет в ITSM системе с меткой `infrastructure` и приоритетом `high`.
- При достижении 80% порога – отправить предупреждение в чат команды (Slack/Telegram).
- При превышении 90% – автоматически увеличить ресурс (например, добавление реплики, расширение диска) если это поддерживается облачным API (Yandex Cloud поддерживает автомасштабирование).
- Для очередей – запустить дополнительных consumer'ов (например, поднять ещё один под MES).
